01

Contexto

Hoje o Singular é um protótipo funcional de alta fidelidade — todas as telas, fluxos, regras de permissão e a experiência de uso já existem e foram validados. O que falta é a “engenharia de bastidor” que o transforma num sistema de produção.

É importante entender a diferença entre o que está pronto e o que precisa ser construído, porque isso define o tamanho real do trabalho que falta:

Hoje (protótipo)Produção (objetivo)
Dados de exemplo num arquivo (data.js)Banco de dados central com os dados reais
Cada pessoa salva no próprio navegadorBase única compartilhada por todos em tempo real
Login simbólico (sem senha real)Autenticação segura com senhas protegidas
Gráficos sobre amostra geradaGráficos sobre números verdadeiros, automáticos
Roda em qualquer navegador isoladoServidor publicando para toda a equipe
Trilha de auditoria localAuditoria persistente e centralizada
✓
A boa notícia: a camada de produto — as ~30 telas e componentes, os fluxos e o design — já está construída e aprovada. Em projetos de software, essa costuma ser a maior parte do esforço (60–70%). O que falta é trabalho de infraestrutura: previsível e bem conhecido.
02

Visão geral da arquitetura

Um sistema de produção se organiza em camadas independentes. Cada uma tem uma responsabilidade clara, e a separação entre elas é o que permite atualizar uma sem quebrar as outras.

🖥️ Frontend — a interface
O que o usuário vê e usa. É o Singular que já existe hoje (telas, gráficos, formulários). Roda no navegador de cada colaborador.
▲ ▼   pedidos e respostas (HTTPS/API)
⚙️ Backend / API — as regras
Recebe os pedidos (“salvar contrato”, “listar propostas”), aplica permissões, valida e conversa com o banco. Aqui também moram login e a auditoria.
▲ ▼   leitura e gravação
🗄️ Banco de dados — a verdade
Onde os dados realmente vivem, de forma permanente e única. Contratos, clientes, propostas, serviços, usuários, logs — tudo central.
▲ ▼   hospedagem
🪟 Infraestrutura — Windows Server 2022
O servidor da unidade que executa o backend e o banco, publica o sistema na rede e roda os backups automáticos.
i
Por que separar em camadas? Porque o código (frontend + backend) e os dados (banco) ficam independentes. Você atualiza o sistema sem tocar nos dados — esse é o segredo para evoluir sem medo, detalhado na seção 9.

04

Do protótipo à produção: o que se reaproveita

Boa parte do que já foi feito vai direto para a produção. O trabalho novo é concentrado e bem delimitado.

✅ Reaproveitado quase integralmente

  • Todas as telas e componentes (dashboard, contratos, clientes, pipeline, financeiro, propostas, serviços, relatórios, usuários, logs).
  • O design system completo: cores SESI, tipografia, tabelas, modais, gráficos, mapa térmico.
  • As regras de permissão por perfil (ADM / Master / Usuário) e os dashboards por setor.
  • Toda a lógica de interface: filtros, buscas, formulários, validações de tela, CRUD visual.

🔧 Construído do zero (o trabalho novo)

  • Backend/API: os “endpoints” que cada tela vai chamar para ler e gravar de verdade.
  • Banco de dados: modelar as tabelas (já temos o formato dos dados como guia).
  • Autenticação real: login com senha protegida, sessões e recuperação de senha.
  • Troca da fonte de dados: onde hoje o frontend lê window.SINGULAR_DATA e o localStorage, passa a chamar a API.
i
O frontend já foi construído esperando dados estruturados. A troca de “ler do arquivo” para “ler da API” é uma alteração cirúrgica numa única camada — não exige reescrever as telas.

Por que PostgreSQL

  • Gratuito e livre para uso comercial, sem pegadinha de licença.
  • Lida tranquilamente com 80+ usuários simultâneos e milhões de registros.
  • Tem transações (ou grava tudo, ou nada — evita dados pela metade) e backups maduros.
  • Roda nativamente em Windows Server 2022.
06

Migração dos dados reais

Esta é a etapa que costuma dar mais trabalho do que parece — não pela tecnologia, mas pela qualidade dos dados de origem. Vale planejar cedo.

1

Levantar as fontes

Mapear de onde vêm os dados verdadeiros: a planilha sistema.xlsx atual, o CRM, o SESIGED e qualquer controle paralelo.

2

Limpar e padronizar

Corrigir nomes duplicados de empresas, CNPJs faltando, datas inconsistentes, status fora do padrão. Dado sujo que entra = relatório errado que sai.

3

Script de importação

Um programa lê a planilha limpa e insere no banco, respeitando as relações (cliente → contrato → serviço). Roda quantas vezes precisar até ficar certo, em ambiente de teste.

4

Conferência

Comparar totais (nº de contratos, somatório de valores, vidas) entre a planilha e o sistema para garantir que nada se perdeu nem duplicou. Só então vira oficial.

!
Atenção: a localização geográfica (cidade/UF) que alimenta o mapa térmico é hoje estimada, pois a planilha não traz esse dado. Para o mapa refletir a realidade, será preciso incluir cidade do cliente na origem dos dados — um campo simples de adicionar.
07

Segurança & permissões

O protótipo já define os perfis; em produção eles passam a ser aplicados também no servidor (não só na tela), o que é o que torna a segurança real.

ItemComo fica em produção
SenhasNunca guardadas em texto puro — armazenadas com hash bcrypt (irreversível).
LoginGera um token de sessão (JWT) com validade; expira e exige novo login.
PermissõesVerificadas no backend a cada pedido — um usuário comum não acessa dados de admin nem “pela URL”.
AuditoriaToda ação relevante gravada no banco: quem, o quê, quando. Imutável.
TráfegoHTTPS obrigatório (certificado), criptografando tudo entre navegador e servidor.
LGPDControle de acesso por perfil + trilha de auditoria já ajudam na conformidade.
★
Integração com o login da instituição: se o SESI usa Active Directory/LDAP, dá para conectar via Keycloak e permitir que cada colaborador entre com o mesmo usuário da rede — sem criar senha nova.
08

Implantação no Windows Server 2022

Passo a passo de alto nível para colocar o sistema no ar dentro do servidor da unidade:

  1. Preparar o servidor: instalar Node.js (LTS), PostgreSQL 16 e Git. (Opcional: Docker Desktop / Docker Engine.)
  2. Criar o banco: subir o PostgreSQL, criar a base singular e um usuário de aplicação com senha forte.
  3. Publicar o código: clonar o repositório Git no servidor (backend + frontend).
  4. Configurar variáveis (arquivo .env): endereço do banco, segredo do JWT, porta. Nunca versionar senhas.
  5. Rodar as migrações: criam as tabelas automaticamente no banco.
  6. Importar os dados reais (seção 6).
  7. Buildar o frontend: gera os arquivos otimizados que o Nginx/IIS vai servir.
  8. Rodar como serviço do Windows (NSSM/PM2): o backend reinicia sozinho se o servidor reiniciar.
  9. Configurar o Nginx/IIS como porta de entrada, com HTTPS e o endereço interno (ex.: singular.sesi.local).
  10. Agendar backups automáticos do banco (seção 10).
i
Com Docker, os passos 1–8 viram praticamente um comando (docker compose up), porque tudo já vai empacotado e configurado. É o caminho mais simples de manter.
09

Atualizações sem perder dados nem quebrar

Esta é a sua principal preocupação — e tem uma resposta tranquilizadora: código e dados são separados. Você atualiza o sistema (código) sem nunca tocar nos dados (banco). São independentes.

O fluxo profissional de atualização

1
Git

Versionamento

Todo o código fica no Git. Cada mudança é registrada com data e autor. Se algo der errado, você volta para a versão anterior em segundos (rollback).

2
Homologação

Testar numa cópia, nunca no ar

Existe um ambiente de teste idêntico ao de produção. A nova funcionalidade é validada lá primeiro. Só depois de aprovada vai para o ambiente real.

3
Migração

Quando a estrutura muda

Se a novidade exige um campo novo (ex.: “telefone do contato”), uma migração adiciona esse campo preservando tudo que já existe. É controlada e reversível — nunca “apagar e recriar”.

4
Deploy

Publicar

Backup do banco → publicar a nova versão do código → conferir. Poucos minutos. Os dados continuam intactos no banco o tempo todo.

Exemplo de uma atualização real

# 1. Pega a nova versão do código (já testada em homologação)
git pull origin main

# 2. Backup do banco ANTES de qualquer coisa (rede de segurança)
pg_dump singular > backup_2026-06-08.sql

# 3. Aplica mudanças de estrutura, preservando os dados
npx prisma migrate deploy

# 4. Reconstrói e reinicia o serviço
npm run build && pm2 restart singular

# Se algo falhar: rollback em segundos
git checkout versão-anterior && pm2 restart singular
✓
Em resumo: o código é versionado e reversível; os dados ficam noutro lugar (banco) e são backupeados. Atualizar funcionalidade não encosta nos dados — e se algo quebrar, você volta atrás. É assim que sistemas sérios rodam por anos recebendo melhorias contínuas.
10

Backup & recuperação

O banco é a parte insubstituível — e por isso protegida em várias camadas:

  • Backup diário automático (tarefa agendada do Windows) — uma cópia completa do banco todo dia.
  • Backup antes de cada atualização — ponto de retorno garantido.
  • Cópia fora do servidor — guardar os backups também em outro local/nuvem, caso o servidor físico falhe.
  • Teste de restauração periódico — backup só vale se você já testou que consegue restaurá-lo.
  • Retenção — manter, por exemplo, os últimos 30 diários + 12 mensais.
!
Regra de ouro (3-2-1): 3 cópias dos dados, em 2 mídias diferentes, sendo 1 fora do local. Simples e salva o projeto em qualquer imprevisto.

Roadmap sugerido por fases

Uma sequência segura, entregando valor a cada etapa em vez de “tudo de uma vez”. Os prazos são estimativas para orientação.

1
~1 semana

Fundação

Repositório Git, banco PostgreSQL, modelagem das tabelas, ambiente de desenvolvimento. Servidor preparado.

2
~1–2 semanas

Backend + autenticação

API dos módulos principais (contratos, clientes, propostas, serviços), login real e permissões aplicadas no servidor.

3
~1 semana

Conectar o frontend

Trocar a fonte de dados do protótipo (arquivo → API). As telas passam a ler e gravar de verdade.

4
~3–5 dias

Migração dos dados reais

Limpeza, importação e conferência da base verdadeira. Gráficos passam a refletir a realidade.

5
~3–5 dias

Implantação + piloto

Publicar no servidor, configurar HTTPS e backups, e rodar um piloto com um grupo pequeno antes de liberar para todos.

6
contínuo

Operação & evolução

Sistema no ar para os 80+ usuários. Novas funcionalidades entram pelo fluxo seguro da seção 9.

i
Estimativa total de um MVP em produção: aproximadamente 5 a 7 semanas de trabalho focado de um desenvolvedor (ou você com a Claude Code), dependendo de integrações e da qualidade dos dados de origem.

Checklist para começar com a Claude Code

Quando for pedir ajuda à Claude Code, leve este documento e estes pontos definidos. Cada item respondido acelera o trabalho e evita retrabalho.

  • Stack escolhida — confirmar: React + NestJS (Node) + PostgreSQL? Ou prefere .NET?
  • Hospedagem — confirmar que será no Windows Server 2022 da unidade, com ou sem Docker.
  • Login — criar usuários no próprio sistema, ou integrar com o Active Directory/LDAP do SESI?
  • Fonte de dados real — ter a planilha/exportação atualizada e definir quem é responsável pela limpeza.
  • Campo de cidade/UF — decidir como obter a localização real dos clientes (para o mapa).
  • Repositório Git — criar (GitHub, GitLab interno ou Gitea) e dar acesso.
  • Política de backup — definir frequência, retenção e onde guardar as cópias.
  • Domínio interno — definir o endereço de acesso (ex.: singular.sesi.local) e o certificado HTTPS.
